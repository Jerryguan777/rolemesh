# 学习笔记:Demystifying Evals for AI Agents(揭开 AI Agent 评测的神秘面纱)

> 原文:Anthropic Engineering Blog — <https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents>
>
> 核心论点:好的评测(evals)能让团队更有信心地发布 AI Agent,把"上线后被动救火"变成"上线前主动验证"。评测把模糊的抱怨("感觉 Agent 变差了")变成可执行的测试用例。

---

## 1. 基本概念与术语

Agent 评测与传统单轮评测的本质区别:传统评测是 "prompt → 响应 → 打分" 的单轮流程;而 Agent 是多轮运行的——跨多次迭代调用工具、修改环境状态、根据中间结果调整策略,因此评测也必须是多轮、面向最终结果的。

关键术语:

| 术语 | 含义 |
|------|------|
| **Task / Problem(任务)** | 一个测试单元,包含明确的输入和成功标准 |
| **Trial(试验)** | 对某任务的一次尝试;多次 trial 用于应对模型的非确定性 |
| **Grader(评分器)** | 对 Agent 表现打分的逻辑;一个任务可挂多个评分器 |
| **Transcript / Trace(轨迹)** | 完整运行记录:输出、工具调用、推理过程、交互内容 |
| **Outcome(结果)** | 环境的最终状态(例如机票是否真的订上了,而不是 Agent"声称"订上了) |
| **Evaluation Harness(评测框架)** | 端到端跑评测的基础设施,支持并发执行 |
| **Agent Harness / Scaffold** | 让模型以 Agent 形态运行的系统(工具、循环、上下文管理等) |
| **Evaluation Suite(评测套件)** | 一组相关任务,衡量某类特定能力 |

评测的两大类别:

- **能力评测(Capability Evals)**:衡量 Agent 能做到什么,起初通过率很低(题目难)。
- **回归评测(Regression Evals)**:维持高通过率,防止性能倒退。
- 二者的关系:能力评测一旦饱和(接近满分),就"毕业"进入回归套件。

## 2. 三类评分器(Grader)及其取舍

### 代码评分器(Code-based)
- **优点**:快、便宜、客观、可复现、易调试。
- **缺点**:对合理的答案变体很脆弱;难以处理主观性任务。
- **手段**:字符串匹配、正则、二元测试、静态分析、结果状态校验。

### 模型评分器(Model-based / LLM-as-judge)
- **优点**:灵活、可扩展、能捕捉细微差别、适合开放式任务。
- **缺点**:非确定性、成本高、必须用人工判断进行校准。
- **手段**:基于 rubric 的打分、自然语言断言、成对比较(pairwise)。

### 人工评分器(Human)
- **优点**:质量的金标准,可对齐专家判断;用于校准模型评分器。
- **缺点**:贵、慢、规模化时需要领域专家。
- **手段**:领域专家评审、众包、抽查(spot-check)、A/B 测试。

## 3. 按 Agent 类型的评测策略

- **编码 Agent**:结果高度可确定化。类似 SWE-bench Verified 的做法:跑测试套件,修复失败测试且不破坏已有测试才算通过。轨迹还可以叠加代码质量启发式规则和模型 rubric(评估工具交互模式)。
- **对话 Agent**:成功是多维的——任务完成度(状态检查)、效率(轮数上限)、交互质量(LLM rubric)。通常需要用第二个 LLM 模拟用户画像(persona)。参考基准:τ²-Bench。
- **研究/调研 Agent**:难点是质量判断主观、且"标准答案"会随时间变化。评测组合:groundedness 检查(结论有出处支撑)、覆盖率检查(关键事实齐全)、信息源质量校验。LLM rubric 需要频繁对齐专家判断。
- **Computer Use Agent**:像人一样通过截图和点击操作。在沙箱环境里运行,校验最终结果(文件状态、数据库变更、UI 属性)。浏览器 Agent 需要在 DOM 交互(消耗大量 token)与截图(更慢但 token 更省)之间权衡。

## 4. 应对非确定性:pass@k 与 pass^k

- **pass@k**:k 次尝试中至少成功一次的概率。适用于"有一个可用解即可"的场景(如生成工具代码)。
- **pass^k**:k 次尝试全部成功的概率。衡量一致性,适用于面向客户、每次都必须可靠的 Agent。
- 二者差距可以非常大:k=10 时 pass@k 可能接近 100%,而 pass^k 可能接近 0%。选错指标会严重误判 Agent 的可用性。

## 5. 从零到有效评测的路线图

### 阶段一:构建数据集
- **第 0 步 — 尽早开始**:从 20–50 个来自真实失败案例的简单任务起步,不要一上来追求几百个。早期改进的效应量大,小样本就够。
- **第 1 步 — 转化手工测试**:把现有的人工检查和用户报告的失败转成测试用例,按用户影响排优先级。
- **第 2 步 — 任务无歧义**:两位领域专家独立判断应得出相同结论;为每个任务写参考解,证明任务可解。
- **第 3 步 — 问题集均衡**:正例、负例都要测,避免类别失衡导致单边优化。

### 阶段二:框架与评分器设计
- **第 4 步 — 稳健的基础设施**:评测中的 Agent 行为要与生产一致;每个 trial 从干净环境启动,杜绝跨 trial 状态共享(会造成相关性失败或不公平优势)。
- **第 5 步 — 深思熟虑的评分器**:能用确定性评分器就用;需要灵活性时才用 LLM 评分器。**评结果,不评路径**——过于死板的步骤检查会惩罚合理的创造性解法。多组件任务要设计部分得分。LLM-as-judge 必须经人工校准验证。

### 阶段三:长期维护
- **第 6 步 — 读轨迹**:定期阅读 transcript,确认评分器工作正常、失败"看起来是公平的"(Agent 确实错了,而不是题目或框架的锅)。
- **第 7 步 — 监控饱和度**:100% 通过率的评测不再提供改进信号;接近饱和时只剩最难的任务,进步会被掩盖。
- **第 8 步 — 维持健康度**:设专门的评测团队负责基础设施,领域专家贡献任务;像维护单元测试一样维护评测。

## 6. 与其他评估手段的组合(瑞士奶酪模型)

没有任何单一手段能捕获所有问题,多层叠加才能互补:

| 方法 | 优点 | 缺点 |
|------|------|------|
| 自动化评测 | 迭代快、可复现、不影响用户、可按 commit 跑 | 前期投入大,需持续维护 |
| 生产监控 | 真实用户行为、规模大、能发现合成评测的盲区 | 被动响应,问题已触达用户 |
| A/B 测试 | 度量真实用户结果、控制混淆变量 | 慢(数天/数周),只能测已部署的变更 |
| 用户反馈 | 暴露预料之外的问题、真实案例 | 稀疏、自选择偏差、偏向严重问题 |
| 轨迹人工审阅 | 建立直觉、发现细微质量问题 | 耗时、不可扩展、覆盖不一致 |
| 系统性人工研究 | 金标准判断、能处理主观任务 | 贵、慢、评审者间一致性难协调 |

## 7. 常见陷阱与质量校验

**常见陷阱:**
- 任务描述有歧义 → 产生噪声,失败源于需求不清而非能力不足;
- 步骤检查过于死板 → 惩罚了合法的创造性解法;
- trial 之间共享状态 → 引入相关性失败或人为夸大表现;
- 评分器 bug 或 harness 限制 → 严重歪曲对 Agent 能力的判断。

**健康信号:** "失败看起来是公平的"——从轨迹能清楚看出 Agent 哪里做错了。反之,大量 trial 全军覆没(如 pass@100 = 0%)通常说明是任务/框架坏了,而不是 Agent 不行。

## 8. 工具与框架(附录)

- **Harbor**:容器化的规模化 Agent 评测;
- **Braintrust**:离线评测 + 生产监控一体;
- **LangSmith / Langfuse**:追踪与数据集管理;
- **Arize Phoenix**:LLM 追踪与调试。

文章强调:**框架本身远不如评测任务的质量重要。**

## 9. 结论与要点回顾

早期投入评测的团队,会从"被动调试"转向"加速开发";评测的价值会随时间复利——前提是把它当作核心基础设施而不是事后补丁。不同 Agent 类型的评测模式各异,但基本功不变:

1. 尽早开始,小规模起步(20–50 个真实任务);
2. 任务来源于真实失败,标准无歧义、可解、正负均衡;
3. 组合使用代码 / 模型 / 人工三类评分器,模型评分器必须经人工校准;
4. 评结果而非路径,每个 trial 环境隔离;
5. 用 pass@k / pass^k 区分"能做到"与"每次都做到";
6. 坚持读轨迹、盯饱和、像维护单元测试一样维护评测;
7. 自动化评测与生产监控、A/B、人工审阅多层互补(瑞士奶酪模型)。
